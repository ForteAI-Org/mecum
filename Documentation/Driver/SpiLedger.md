# SPI ledger

Private primitives and fragile public behaviours the research met, with what
happened on which build. This file is the graveyard and the archive: what the
kit *uses* lives in `Sources/PrivateSymbols/Ledger/validated-builds.json`, and
what the compatibility suite finds lives in `docs/compatibility/Build<build>.md`.

All findings below are from macOS 27.0 build 26A5425a unless stated otherwise.

## Used by the kit (details in the JSON ledger)

| Primitive | Kind | Why it is needed |
|---|---|---|
| `SLSMainConnectionID`, `SLSGetWindowOwner`, `SLSGetConnectionPSN` | symbol | window identity re-read before posting, and the owner connection a routed event needs |
| `SLEventRecordPointer` | symbol | the record's declared length (0xF8) is the kit's only whole-record check |
| `SLPSPostEventRecordTo` | symbol | Preparation: makes the target window active and key inside its own process only |
| `CGEventSetWindowLocation` | symbol | writes the window-local point (record 0x20 / 0x28) without a pointer store |
| `CGEvent` integer fields 51 and 52 | field | window number and owner connection, cross-validated by round-trip against 0x3C / 0x40 |
| `CGVirtualDisplay`, `CGVirtualDisplayDescriptor`, `CGVirtualDisplayMode`, `CGVirtualDisplaySettings` | class | the Virtual Display; released, not closed, to remove it |
| `_SLPSGetFrontProcess` | symbol | read-only PSN witness for opt-in focus recovery; exact underscore ABI verified on 26A5425a in the independent sampler and live calls. Required by the optional facility, not promoted into the build ledger. The retained measurement bundles record latency uncertainty and the unresolved AX observation failure |
| `_AXUIElementGetWindow` | symbol | maps an accessibility window element to its Window ID |
| The record's type byte at 0x08 | behavior | it is the `rawValue` of the event's own `CGEventType`, across the whole table: 0x01 / 0x02 left button down and up, **0x03 / 0x04 right**, 0x0A / 0x0B keyboard, 0x16 scroll, and **0x0C for a modifier transition**. Read back out of records CoreGraphics built, one type at a time. The `flagsChanged` byte was added on 2026-09-14: CoreGraphics offers no constructor for a transition, so the event is built as a keyboard event and its `type` reassigned, and the check verifies that the reassignment sticks before it reads anything. On 26A5425a the assignment held, the record declared 248, and 0x08 carried 0x0C. `RecordLayout.verifyFlagsChangedRecord()` is the check and `SystemGateHostTests` is its oracle. It is **not** a Facility requirement and adds no row to the build ledger: a new `untested` requirement would make the whole Input Facility unvalidated on a build nobody has promoted, so the modifier policy that posts transitions closes on this check's own live answer instead. `RecordLayout.typeByte(of:)` states the rule so no caller writes a number down; the window server's own record types outside the public enumeration, such as the Preparation's activation record at 0x0D, are not covered by it |
| `CGWindowLevelForKey(.popUpMenuWindow)` with `CGWindowListCopyWindowInfo` filtered by owner and level | behavior | the **only** oracle for an open contextual menu, and it is level 101 on 26A5425a, read from the system rather than written down. `WindowServerProbe.menuWindows(ownedBy:)` reads it and `AgentSeat.useContextMenu` refuses when it answers nothing: a contextual menu is absent from the target's accessibility tree on both families, so no other reading can see one |
| `AXManualAccessibility` | behavior | undocumented accessibility attribute. Written by `TargetReader` only, on the application element, before every reading: Chromium, Electron and CEF build their tree solely for a client that asks, so without it a target exposes a handful of elements and no text. The write's own answer is the gate, because a target that refuses the attribute is not of that family and needs no wait. Verified on 26A5425a against three background Electron targets (see the behaviours table). It is the one write the kit makes besides placement, and ADR 0009 says why |

## Verified but not used

| Primitive | What happened | Why it is out |
|---|---|---|
| `SLEventPostToPid` | delivers, same effect and same cost as `CGEventPostToPid` | one route is enough; the public one is cheaper to defend |
| `SLEventSetIntegerValueField` (fields 0, 1, 3, 7, 40) | writes the record | the public `setIntegerValueField` writes the same bytes |
| `SLEventSetIntegerValueField` (field 58) | writes the event timestamp (0x30-0x37), not a gesture id | the "Chromium stamping" it belonged to changes no outcome |
| Chromium field stamping as a whole | click passed with it and without it | Preparation is the only ingredient that decides a Chromium click |
| `mouseMoved` primer with 12/28 ms pacing | click passed without it on both families | plain down/up plus Preparation is the recipe |

## Discarded

| Primitive | What happened |
|---|---|
| **An insertion costs a constant, not a price per character** (ticket B4) | measured on 26A428, 14 September 2026, both families. Every length arrived **whole** up to and including the declared ceiling of 8192 UTF-16 code units: 512, 1024, 2048, 4096 and 8192, on an AppKit target and a Chromium renderer alike, two events each time. The cost does not follow the length. A Chromium renderer took 165 ms for 512 units and 169 ms for 8192, because almost all of it is the Preparation and the 150 ms settle that family declares for an insertion; an AppKit target went from 4 ms to 11 ms across the same range. Per unit that reads as 322 down to 20,6 microseconds on the browser and 8,4 down to 1,4 on the native control, which is one fixed cost spread over more text rather than text getting cheaper. The consequence is a design one: a smaller chunk buys nothing and pays the constant again, so `TextDeliveryLimits.measured` sits at the ceiling a single Command may carry and chunking begins exactly where a Command would be refused. Above the ceiling the refusal happens as declared, and on a family that prepares it arrives wrapped in an `InputPreparationFailure` that also reports the Preparation was given back |
| **`CGEvent` integer field `keyboardEventAutorepeat`** (ticket A3) | **an event carrying it is not delivered at all, to either target family.** Measured on 26A428, 14 September 2026: twelve counts, 1, 4, 16 and 32, across three inter-repeat intervals, 0, 8 and 33 ms, against an AppKit target and a Chromium renderer. Every one of the 24 rows received **zero** of the repeats it posted, while the ordinary key down that opened each run arrived every time and a control of four ordinary presses arrived four times out of four on both families. The pacing changed nothing, which is what rules out speed and leaves the field itself. With the field no longer written, the identical sweep received **every** repeat: 1, 4, 16 and 32 out of 1, 4, 16 and 32, on both families, at all three intervals. So the kit posts a repeat as ordinary key downs and `KeyPhase.repeated` says what that gives up: a target reading the field, or `event.repeat` in a web page, sees discrete presses rather than a run marked as a repeat |
| **The pause between repeats is not needed for delivery** (ticket A3) | at an interval of zero all 32 repeats arrived on both families, in 782 ms against 1909 ms at the system's own 33 ms: the pacing costs about 1,1 s per 32 repeats and delivers exactly the same events. `KeyRepeatPacing.systemDefault` stays the default anyway, because what was measured is **delivery** and not what a target does with the gap: an application that accelerates while a key is held reads the interval, and nothing here measured that. A caller that needs the speed can set zero knowing the events arrive. The cap of 32 on `KeyPhase.maximumRepeatCount` is now a measured cost rather than a reasoning: at the system interval those 32 hold the target's exclusion for 1,9 s |
| **Every menu key equivalent, not just Command and V** (ticket A8) | **measured on 26A428, 14 September 2026, both target families and both modifier policies: four runs, and all four agree.** Command and C, Command and V, Command and A, Command and Z, Command and Shift and Z and Command and Shift and S are **delivered and acted on by none**, on an AppKit target and on a Chromium renderer alike. Every row asserted delivery separately from effect, and delivery held on every one of them: the key events arrive, with the right modifiers on them, and nothing happens. What the Ledger recorded for one shortcut is a property of the mechanism. **Two controls make the six mean something.** Option and the right arrow was delivered **and acted on** on both families, moving the caret by a word. Escape was delivered and acted on through the AppKit target's own `cancelOperation:`. Both are answered by the responder chain and the standard key bindings, with no menu in the path, and both worked. So the events are not dropped, malformed or misrouted: they arrive, and a menu that belongs to the frontmost application does not answer them. Without a row that passes, the six would be indistinguishable from a driver that cannot deliver. **The modifier policy changes nothing**, which was the open half of the spike. The same matrix ran under `ModifierPolicy.flagsChanged`, posting real modifier transitions instead of stamping the modifiers on the key: Command and C went from 2 events to 4 and Command and Shift and Z from 2 to 6, so the transitions really went out and were counted. Every row landed identically on both families. `.flagsChanged` stays in the kit as a policy no shipped platform asks for, and ADR 0011 keeps `.eventFlags` as the default for the measured reason rather than the reasoned one. **What the measurement does not cover.** The build is not promoted, so every Receipt carries `unvalidatedBuild` and the run used the research opt in; the self checks passed, which is the part that protects the record offsets, but the Ledger has no entry for 26A428. The initial Chromium Escape row had no effect oracle. The acceptance follow-up now opens a native HTML dialog in the owned probe page and requires its cancel event and closed state; that row passes. Save is checked through a new visible window owned by the target, and remains delivered without effect. See the retained acceptance evidence for the revised oracles and the repeat-pacing qualification |
| `InputCommand.paste`, the Command and V key equivalent | **delivered to both target families and acted on by neither.** Two events go out, the receipt says so, and the target's own diagnostic sees them as a Command and V keyDown with `characters` and `charactersIgnoringModifiers` both `v`. At that same moment the target reports, from the inside, `NSApp.isActive` true, `NSApp.keyWindow` equal to its own window, `isKeyWindow` true, an Edit menu with a Paste item installed, and `NSApp.target(forAction: paste:)` resolving to its own `NSTextView`: every precondition the mechanism has, and nothing is pasted. The same on a Chromium renderer, whose page never sees a `paste` event. The reason is structural: a paste is not *delivered* like a key press, it is **resolved** by the application's menu, and a menu belongs to the frontmost application, which the kit may never become. Two things were tried and changed nothing: holding the Preparation for 60 ms after the events, in case the target dequeued them after the restore, and running the row before the click and drag rows, in case the first responder had moved. The Command and both platforms' Preparation for it stay in the kit, and the two Live rows stay as `withKnownIssue`, because the row is the detector for the build where this changes |
| A private `NSPasteboard(name:)` as the source of a paste | ignored. With the general pasteboard holding one marker and a private pasteboard holding another, the target read the general one; nothing public or private carries a pasteboard name on an event, and the only reader-side entry point is `readSelection(from:)`, which the target calls itself. This is what makes replacing the person's clipboard unavoidable for any paste, and it is why the replacement is gated instead of hidden |
| Reading the person's clipboard as a way to read a target | not needed and not reachable. `TargetReader` already answers with `value` and `selectedText` per node, in one read of the tree with no mutation of anything: 50 nodes on a Chrome window and 628 to 1595 on Electron targets, 141 to 216 ms. A clipboard read would need a selection in the target first, and selecting there means either a synthetic drag, which a standard text view has never accepted from an inactive window, or writing `AXSelectedTextRange`, which the isolation invariant forbids the kit; a Command and C is the same menu key equivalent that does not work. So the kit ships **no clipboard read API**, and the person's clipboard is read only inside a loan, only to be given back, never returned to a caller and never logged |
| `SLSSetPreventsActivation` | returned zero, the window tag never changed, the drag left the selection untouched |
| `SLSSetMouseFocusWindow` | accepted and restored the mouse focus, but a standard `NSTextView` still refused the selection |
| `SLEventPostToPSN`, `SLEventPostEventToPSN` | error -600 on a modern process |
| `_SLPSSetFrontProcessWithOptions` | excluded from background input; now used only by the opt-in, destination-bound user focus recovery of ADR 0010. Focused Print experiments are recorded separately from build-ledger promotion |
| `SLSSetCursorRegionLock`, `SLSSetCursorRestrictionMode` | accepted, cursor still entered the virtual display; the HID event tap replaced them |
| `SLSHWCaptureWindowList`, `SLSGetSurfaceFrontBufferID`, `SLSScreenshot`, `SLSHWCaptureStreamCreateWithWindow` | on a Stage Manager stashed window: same thumbnail, no surface, status -1, or a hang during create |
| Three point drag (down, one move, up) | delivered to the process on both families and moved no control on Chromium, prepared or not | the paced path (opening `mouseMoved`, eight steps, 24/16/12 ms) is the only drag that works, so it is the only drag the kit builds |
| `BackgroundClickDriver` and its two profiles | both passed on the fixture; only the prepared one passed on Chromium | one recipe covers both families, so the profile switch and its UI are gone (phase 5) |
| Text selection by synthetic drag | never accepted by a standard `NSTextView` from an inactive window, on any recipe: plain drag, Shift-drag, primed drag and mouse focus set first |
| `AXSelectedTextRange` written on the target | selects the text and is a **write to the target**, which the isolation invariant forbids the kit: only the consumer may write through accessibility, and the kit's own use of it is placement (ADR 0004) |
| `SLSPostEvent`, `SLSPostMouseEvent*`, `SLPostKeyboardEvent` and relatives | never authorised: they risk global routing onto the User Seat |
| The paste through the private record, unstamped | delivered, never resolved. `SLPSPostEventRecordTo` returns 0 for both the key down and the key up, the target receives them, nothing is pasted |
| The paste through the private record, **stamped** with window and connection | identical. Stamping fields 51 and 52 is what carries a **mouse** event to a window, because the window server hit-tests coordinates; a key equivalent is resolved by the application's menu, a subsystem those record fields never reach. This was the last untried variable and it changed nothing |
| The paste through the private record, stamped and with the Preparation applied | identical. The Preparation moves the target's internal belief about being active; it does not move which application owns the menu bar, which is a system fact about the real frontmost |
| `AXUIElementPostKeyboardEvent` for the paste | returns 0 four times over, events received, nothing pasted |
| `SLEventPostToPid` for the paste | delivered, not acted on |
| An accessibility press on the target's own Paste menu item | `AXPress` returns 0 and the item reads `enabled false` while the application is in the background. The same press on the same item works when the application is frontmost, which is the experiment that names the cause |
| A context menu, opened by right click or by `AXShowMenu`, to click Paste inside it | **withdrawn: the reading was wrong, and it was wrong in two ways at once.** It is now a shipped primitive, `AgentSeat.useContextMenu`, and the row it replaces is in the behaviours table below. The first defect was the oracle: the reading asked the target's accessibility tree, and a contextual menu is not in that tree at all, so it answered "no menu" for a menu that was on the screen. The second was the recipe: the Preparation's restore dismisses an open menu, and the old probe restored after 300 ms and then looked. A third thing, unrelated to either, explains the rest of the negatives: an unrouted right click reaches the process with `windowNumber == 0` and no view to receive it, so it opens nothing |
| One delivered keystroke as a way to wake a Chromium accessibility tree | does not wake it: 36 nodes cold, 37 after the keystroke, no web area either way. A keystroke gives a renderer node focus in a tree that is **already** awake; it does not build the tree |

## Discarded shapes of the calling code

Not primitives, so not in the JSON ledger, but deleted for a measured reason and
recorded here so nobody rebuilds them. All on 26A5425a.

| What | Why it is gone |
|---|---|
| `primedDrag`, `pacedDrag` and `modifiedDrag` as three Command cases | one `drag(points, flags:)` covers all three: the primer changed no outcome, the pacing is the platform's `DragPacing`, and the modifier is `flags`. Three cases were three chances for a call site to pick the one that does not work on Chromium |
| `postKeyboardZ`, `postMouseClickViaSkyLightEventRecord`, `postScrollViaSkyLightEventRecord`, `postTextSelectionDragViaSkyLightEventRecord` | one function per action, each with its own copy of the routing: `InputCommand` plus one driver covers every one of them, and the text selection never worked at all |
| `perform(kind)` and `TestKind` | a dispatcher over a suite of buttons that drove the fixture from a UI. The same effects are asserted by `LiveTests`, where a failure is a red run and not a paragraph somebody reads |
| The click profile popups | a menu that let a person choose between two posting recipes. One recipe covers both target families, so the choice could only be wrong |
| `lastPrivatePostError`, `lastPrivateRouteDescription`, `pendingFixtureClickProfile` | consumer state from the era of several routes and several profiles. `InputReceipt` carries the route as fields, so a report reads them and nothing has to be remembered between two actions |
| `scheduledWorkItems` | a list of `DispatchWorkItem` an action cancelled on its way out. The seat's Turn is what bounds an action now, and a Command is never split into scheduled pieces |
| The virtual capture test in the consumer's UI | a button that orchestrated a capture of the fixture on the virtual display and compared two frames. `CaptureHostTests` takes the same stream and the same `still()` on a real virtual display and compares them to `SCScreenshotManager` on the same filter, in a run that fails |
| `KitLinkProbe.swift` | a file whose only job was proving the consumer could link the package. The consumer calls the kit on every path now, and `MemberImportVisibility` turns a missing import into a compile error |

## Where the symbols actually live

Measured with `dladdr` at runtime, not read off an export list: `CGEventSetWindowLocation`
is defined in **SkyLight** and merely re-exported by CoreGraphics, and `objc_msgSend`
lives in `/usr/lib/objc/libobjcMsgSend.dylib`. `dlopen(nil, RTLD_LAZY)` searches only the
images already loaded, so a binary that does not link CoreGraphics finds none of the
SkyLight symbols: the symbol table re-opens the primitive's own image and retries before
calling a symbol missing.

## Fragile public behaviours

**A live HID tap plus repeated virtual display creation ends the process, with exit code 0.**
Running the whole host tier in one process stops mid-run after the seat cycle, at the start of
the virtual display suite, with no summary line and a green exit status. Reproduced without any
session code by holding a `CursorFence` around repeated display creations; six displays without a
fence pass, eight from a synchronous `main` pass. Consequence for the build: the host tier runs as
two commands **and** the runner must assert the expected test count, because the process exit
status cannot be trusted to mean the run finished.


| Behaviour | Observed |
|---|---|
| `CGDisplayIsOnline` / `CGDisplayIsActive` | return `0xFFFFFFFF`, not 0, for a display id that no longer exists: membership of `CGGetOnlineDisplayList` is the only honest check |
| `SCStreamConfiguration` defaults | `minimumFrameInterval` 1/60, `queueDepth` 8, `pixelFormat` 420v, all different from the public documentation |
| `CALayer.contents` accepts an `IOSurface` | documented in `CALayer.h` and **not** on the web, where only `CGImage` and `NSImage` are listed. The zero-copy Monitor stands on it, so a unit test assigns a real surface to a `MonitorLayer` |
| `CGVirtualDisplay` lifetime | releasing the object removes the display within about 100 ms; there is no removal selector |
| `NSWindow` created with a global frame on another screen | AppKit re-places it on the main screen; the `screen:` initialiser is required |
| `AXManualAccessibility` | **works, and the wait is the whole difficulty**. Measured on 26A5425a, 09/09/2026, on three background Electron windows read through the kit's own probe: Slack 628 nodes and 178 text carrying nodes in 141 ms, GitHub Desktop 1452 nodes and 934 in 191 ms, Notion 1595 nodes and 545 in 216 ms, `AXWebArea` present in all three, none of them in front. A cold target is slow: Notion still answered with 15 nodes at one second after the write and with 1673 at two, which is why the ceiling is 3 s and not the 400 ms of the blind sleep it replaces. **The trap is the readiness signal.** An earlier phase 8 reading concluded the attribute bought nothing on Chrome; it was produced by a wait that returned as soon as a *depth limited* descendant count stopped changing, and such a count is blind here: an Electron window reports seven descendants down to depth three whether its tree holds 1452 nodes or 15, so the wait ended inside 60 ms and read the thin tree every time. The condition is now a capped count with no depth limit, and growth has to be seen before stability means anything. **Google Chrome, re-read on 09/09/2026 with the corrected wait, still answers with browser chrome and nothing else**: 49 nodes and then 50 two seconds apart, roles `AXButton AXGroup AXPopUpButton AXRadioButton AXStaticText AXTabGroup AXTextField AXToolbar AXWindow`, no `AXWebArea` and no word of the page, on a full size window in the background, reproduced in two separate runs of `WindowReaderLiveTests`. So the attribute's answer on this build splits by application and not by family: Electron and CEF targets build their tree for a background client, Google Chrome does not. The write stays, because it costs one accessibility call and it is what the Electron targets need; the two Chrome assertions stay `withKnownIssue` because the day Chrome answers, the run fails and they become plain assertions |
| Stage Manager | stashes every inactive window on a display down to a thumbnail, so a routed event reaches the process but lands outside the control. **Not reproducible on demand**: with `GloballyEnabled = 1` and `AppWindowGroupingBehavior = 1` on 09/09/2026, neither the `stage` benchmark (a second process's window adopted on the Virtual Display, this driver's own window brought forward) nor the Live matrix (an instrumented target and a Chrome window adopted one at a time) got a single window stashed, over five benchmark cycles and two adoptions. Ticket 16 saw a stash on 08/09/2026 on the same machine. Consequence: `stage` is a **verified primitive with no measurement of its own**, because nothing can manufacture the stash without activating an application, and activating one is what the kit must never do |
| `NSPasteboardItem.data(forType:)` on a promised type | **raises and kills the reading process.** On a local `NSFilePromiseProvider`, reading `com.apple.pasteboard.promised-suggested-file-name` raised `NSInternalInconsistencyException`, "Invalid parameter not satisfying: string", inside `-[_CFPasteboardEntry resolvePromisedDataWithCompletionQueue:isLocalPromise:completionHandler:]`, which called `-[NSPasteboardItem setString:forType:]` with something that was not a string; Swift cannot catch it and the process died. Its four sibling types answered 116, 0, 17 and 8 bytes, so a promise is also **not restorable**: what a save could put back is bytes, and what was there was a promise the receiver was meant to fulfil through a callback. Consequence: `ClipboardContents.read` lists every item's types first and refuses on a promised identifier before asking for a single byte, and refuses again on the first type whose bytes come back `nil`. Nothing public marks a type as promised, so the test is the identifier: anything containing `promise` plus the legacy `CorePasteboardFlavorType 0x66737270`. A third-party lazy provider under a name of its own is not recognisable this way and is the residual risk, bounded by the second refusal |
| `NSPasteboard.changeCount` | moves on **ownership** and not on content: `clearContents()` returns the new value and a further `setData` under the same ownership does not move it, while another process's clear moves it by one. It is the whole evidence a restore has: equal means nobody wrote after us. The window it cannot close is between reading the count and taking the pasteboard, measured at 114 us p50 and 172 us p95 over a 4 KB clipboard in one type, because the pasteboard offers no compare and set. A clipboard manager that watches the count sees the loan's own text: the restore puts the person's content back, it cannot unsee it |
| `SLPSPostEventRecordTo` cost | one record is a window server round trip: a whole Preparation cycle (three records applied, one restored) measured 133 to 147 us at p50 and 213 to 250 us at p95, with about 270 allocations charged inside the call. It is IPC, not computation, and it is why the settle and the Preparation are both kept off the warm path's budget |
| `CGEventPostToPid` aimed at the calling process | ends the process. Measured in the Host tier of phase 7: a `swiftpm-testing-helper` that posted a click to its own window died at the `postToPid` call, exit code 0, no crash report, with both events already routed and the window server's identity re-read successful. It is the reason the Host tier's cycle stops before the post and the Live tier owns the whole cycle |
| `NSFont.monospacedSystemFont(ofSize:weight:)` | **answers nil sometimes, into a non-optional**, and the process dies. Seen twice in a row on 09/09/2026 inside `SeatBench monitor-60`, whose scene view puts the answer straight into a text attributes dictionary: `NSInvalidArgumentException`, "attempt to insert nil object from objects[0]", raised by `NSString.draw(at:withAttributes:)` during a CoreAnimation commit, with the whole benchmark exiting non-zero. The same call answered `.AppleSystemUIFontMonospaced-Regular` in a plain process at the same minute, and the same benchmark passed three times the same evening, so it is a state of the font system and not of the code. Not reproducible on demand, so nothing has been changed for it: a workaround that cannot be tested against the failure is a guess. What it costs today is a `make bench` that has to be rerun |
| `Double.init` unapplied on a `UInt64` | resolves to `Double(bitPattern:)`, not to the numeric conversion. `array.map(Double.init)` over nanoseconds reported every 757 ms recovery as 3,7e-315, so every benchmark that maps integers to doubles writes the closure out |
| a live `CGEventTap` while virtual displays come and go | in a `swift test` process, a run that holds a fence across several display creations dies partway through with a SIGSEGV inside `objc_release` during an autorelease pool pop on the main queue. Reproduced with no session code: acquiring a fence around `VirtualDisplayHostTests.aSecondDisplayInTheSameProcess` fails the same way. Six displays without a fence pass, eight from a synchronous `main` pass. Not understood; the Host tier runs the seat cycle in its own invocation because of it |
| `SLPSPostEventRecordTo` on a key equivalent | **returns 0 whether the event was resolved or ignored.** No return code separates the two, so a road built on it can never be made fail-closed on its result: the only proof is reading the target's own state afterwards. Three outcomes exist and only two are distinguishable from the caller, which is why the delivered-and-ignored case went unnoticed for a whole phase |
| The 248-byte event record, keyboard shape | the type byte at 0x08 is `0x0A` for a key down and `0x0B` for a key up; the declared length at 0x04 is 248 (0x F8) with 256 allocated; the Command modifier is `0x00100000` in the dword at 0x38, whose byte 0x3A the kit already writes as 0x10. A well-formed record that is accepted and ignored is not a malformed record, and knowing the type byte is what tells them apart |
| A key event carrying the whole string, on a native AppKit target | **puts 8192 characters into a background window in at most 295 ms, on two events, with one change notification.** A keyboard event with virtual key 0 and `CGEventKeyboardSetUnicodeString` of the entire string, posted with `CGEventPostToPid` and no Preparation: the target's own field holds all of it and its editor reports **one** edit. The same string as one key pair per character costs 16384 events and 82 to 92 s, about 11 ms per character, and the per-character cost grows with what the field already holds; the inserted total does not move between 128 characters and 8192. Measured on 26A5425a, 09/09/2026, against an instrumented target this measurement launches, in four window states: frontmost, background, adopted onto the Virtual Display and raised there. The 295 ms is an upper bound and not the figure: the target publishes its state twice a second, so anything it reports under about 500 ms means the change was already applied when it next published |
| The same key event on a Chromium renderer | **needs the Preparation, in every window state, and needs a longer settle after it than any other Command.** Unprepared it is delivered and refused: the page's `keydown` fires and the focused field's `keydown` fires, both counted, and nothing is inserted, at 2 characters and at 8192 alike, frontmost, in the background, adopted and raised, over five runs and about thirty attempts with not one insertion. One character on the same event, which is what a typed string is made of, passes unprepared in every one of those states, so the discriminator is the shape of the event and not where the window sits, and that is what makes it expressible as a policy per Command. Prepared, the settle decides: with the window on the virtual display, 30 ms inserts about seven times in ten, 60 ms eleven in twelve, 100 ms and 150 ms twelve out of twelve each, so `ChromiumPlatform` answers 150 ms for this Command and 30 ms for every other. **The failure has no error anywhere**: `CGEventPostToPid` returns, the receipt says two events went out, and the field is empty, which is why the only proof is the target's own counter |
| The same key event at a Stage Manager thumbnail | **refused at every settle tried.** On a physical display, with the person's Stage Manager holding the target stashed at 99 by 132 points, a prepared bulk insertion failed at 60 and at 225 ms while the same Command at the same settle passed twelve times out of twelve with the window at full size on the virtual display. A seat stages a window before posting to it, so it does not meet this; a caller that posts at an unstaged window does, and gets no error when it happens |
| A contextual menu in a background application | **opens, on both families, and is usable.** Re-measured on 09/09/2026 after an earlier reading concluded the opposite. The click has to be **routed**: unrouted it reaches the process with `windowNumber == 0` and no view to deliver it to and nothing happens, which is half the old negatives. Routed, the window server shows a window owned by the target at the pop up menu level, on screen, at +43 to +97 ms on a native target and +314 ms on a browser; the accessibility tree shows nothing at any point, which is the other half. Measured routes, three rounds each on the instrumented target: routed public post yes, routed private record yes, `AXShowMenu` on the element yes, unrouted no. Control: a **left** click at the same point, routed and prepared, opens no menu, which is what makes the right button's result a fact about the right button |
| An open contextual menu and the User Seat | **the frontmost application never moves.** Sampled every 30 ms across the click, the menu's whole life and the teardown, on the physical display and on the Virtual Display: the frontmost appears once at the start and does not change again, and the target reports `active false, key false` about itself throughout. What it costs instead is visible: the menu is **drawn**, 115 by 34 points on the instrumented target and 201 by 377 on a browser, and while it is up the target runs a modal tracking loop instead of its own event loop |
| A contextual menu on the Virtual Display | **it follows the target's window and stays inside that display**, so on a seat the person sees nothing at all. Measured 09/09/2026 on both families, with the window adopted and staged by the seat: the display at (1512, 982) 2560 by 1440, the native menu at (2793, 1806) 115 by 34 and the browser's at (2793, 1652) 242 by 661, each wholly contained, with zero physical events during the runs. This is what makes the primitive shippable rather than a visible interference |
| The Preparation around a right click | **harmful, and it is the restore that harms.** A menu's tracking loop reads the deactivation record as an application switch and dismisses on it: prepared and restored, a menu lives 413 to 453 ms; the same click unprepared is still open at 1,9 s. So `ChromiumPlatform.preparation(for: .click(_, .right))` is `.none`, which is the one row of that table where preparing is worse than not preparing, and the family that needs the Preparation for every other mouse Command opens its menu without one |
| A Preparation applied and restored as a way to close a menu | **the same property, used as the lever: 50 ms.** It is the first of the two nets in `AgentSeat.useContextMenu`; an Escape routed to the process is the second, and it reaches whatever holds the key inside the target, which while a menu is tracking is the menu. A menu that survives both is `SeatIssue.contextMenuLeftOpen`, critical, plus a thrown refusal: an open menu is a modal loop in somebody else's process and it is the worst thing the kit can leave behind |
| Choosing an item by clicking the menu's own window | **works on both families, with the kit's plain click.** A left click routed to the **menu's** Window ID, with the window-local point and fields 51 and 52, and the frame taken from `CGWindowListCopyWindowInfo`: `WindowServerProbe.geometry(of:)` was written for a window somebody named in advance and a menu window is not one. Six of six in the exploratory run and every run since. The opening `mouseMoved` a menu's tracking loop might have been thought to need changes nothing: measured with and without it as the only difference, the native target reports the item chosen either way, so the kit's no-primer rule holds here as everywhere else. The menu dismisses itself 457 ms after the click on a native target and sooner on a browser, which is why the teardown waits 700 ms for it before pulling a lever |
| Choosing an item on a **Chromium** target | **depends on the chosen command, not merely the family.** The 09/09 conclusion was based on a blind click at the menu rectangle centre. On 10/09, the captured menu places Print at that point. Two independent direct-driver trials and the corrected `ContextMenuLiveTests` chose **Select All** by its captured text rectangle: the page confirmed selection from 5 to 10 characters, with no activation during the choice. The final expanded matrix also chose **Undo** and **Redo**, proving `changed → menu probe → changed` while ChatGPT stayed frontmost, with zero physical events and no cursor movement. It holds Chrome on the virtual display until all three effects have been read. The test now refuses unidentified items, confirms the page effect, and asserts that the User Seat stays intact. The existing delayed-activation guard remains: other commands can legitimately activate their application. This ledger entry retains the source conclusions and evidence. |
| The items of an open contextual menu | **readable on AppKit, not on Chromium.** An `NSMenu` opened as a contextual menu is an `AXMenu` child of the **window** element, not of the application element, which is where the menu bar lives and where the earlier reading looked. A Chromium contextual menu is absent from the accessibility tree for the whole time its window is on the screen, with `AXManualAccessibility` written and the rest of the browser's tree readable. `WindowReader.contextMenu` answers the two cases apart rather than returning an empty list for both: on that family the caller has a rectangle it cannot read, and geometry or a capture is what is left |
| The window server's idea of key focus while a menu is open | **not measured.** `SLPSGetFrontProcess`, `SLPSGetKeyFocusProcess` and `SLPSGetTypingFocusProcess` all resolve and all three killed the process with SIGBUS when called as `(ProcessSerialNumber *) -> OSStatus`, twice over, before printing a line. Their real argument list is something else and it was not guessed a third time. What can be said is what was measured: `NSWorkspace`'s frontmost never moved in any row |
| A typed string on a Chromium renderer, unprepared | **arrives.** Re-measured on 09/09/2026 because a reading had concluded the opposite, in four window states, with one key pair per character: 16 characters arrive in about 230 ms frontmost, in the background, adopted and raised, and 8192 in 3,4 to 5,4 s. The contrary reading was taken with the whole string on **one** key event, which is the row above and a different Command; nothing in `.text` needs the Preparation on this build. The line `ChromiumPlatform.preparation(for: .text) == .none` therefore stands, and a consumer relying on it was never getting anything wrong |
| An element's accessibility value, written | puts text into a background target with no clipboard and no events at all: verified at 200 characters on a native window and on a browser launched with `--force-renderer-accessibility`, with one change notification instead of one per character. It is the consumer's road, not the kit's, and it needs re-reading to be believed |
| An element's accessibility value on a framework editor | **declares itself settable, accepts the write, and reads back at least one write behind.** Measured on a message composer: 200 characters never appeared within eight seconds of polling, and appeared only when the next write went out. The write cannot be confirmed, which is the one property that made this road preferable to a paste, so on such a target it is skipped by policy rather than attempted and guessed |
| A key event carrying a unicode payload, at a client that is **already composing** | **dropped, and the composition is left standing.** Measured 14/09/2026 on 26A428 against an instrumented AppKit target holding four marked units: the string never appeared in the field and the marked range was still four units afterwards. The control is in the same run and is what makes it a fact: the identical `.insertText` to the same window, with nothing composing, arrived. What it is evidence about is the **client** half of the protocol. The target arms itself by calling `setMarkedText`, which is exactly what an input method calls on its client, so the text view really holds marked text; what is missing is an input source that owns the session and would see the event first, and a row that needed Japanese installed would measure nothing on anybody else's machine. So this says what a composing text view does with an insertion, and it does not speak for any particular input method. Consequence: `.insertText` at a target that may be composing is the delivered-and-ignored case, which has no return code, and the documentation says dropped instead of unknown |
| The person's own held modifier and an event from a private source | **stays out.** Measured 15/09/2026 on 26A428 with a hand on the keyboard: with Shift physically down, verified down at the instant of the post through `CGEventSource.flagsState(.hidSystemState)`, the kit's key event reached a browser probe page carrying a modifier mask of **zero**. Until this row ran, `CGEventSource(stateID: .privateState)` keeping the person's state out was a documented intention and nothing more. The oracle is the point: the same zero is what an untouched keyboard produces, so the row reads the hardware state as well and refuses to conclude anything when nobody was holding the key. Only the **incoming** direction is measured. The outgoing one cannot be read through this target: the person's own keystrokes go to whatever window is in front of them, which is never the probe page on the seat's display |
| A modifier transition the kit posts and never releases | **rides every later event of that session, and the person's own key does not clear it.** Measured 15/09/2026 on 26A428: a Command down posted as a real `flagsChanged` and deliberately left open, after which every further event the kit posted arrived at the target with the Command bit set; the person then pressed and released their physical Command key, verified through `hidSystemState`, and the next event still carried it. So a stranded modifier is not self healing and nothing outside the kit will close it: the only thing that clears it is the kit posting the inverse transition, which is why ADR 0011 makes press, key, inverse release one atomic sequence and why `AgentSeat` refuses to give a Turn back with keys still held. What it costs if it ever escapes is measured here too: it is permanent for the target, not transient |

## Defects of the measurement itself, found on 09/09/2026 and corrected

None of these is a defect of the kit. Every one of them made a green run mean
something it did not mean, which is worse than a red one.

| Defect | What it did | What it is now |
|---|---|---|
| The two Live suites ran in parallel | suites are serialized within themselves, and different suites still run against each other. Both Live suites drive the same browser and the process admits one virtual display at a time, so one suite quit the window the other had adopted: `.processUnavailable` on the browser's pid, and the reader's own row disturbed by the other suite's target coming up. Never seen before because the tier had only ever been run one filter at a time | `make live-tests` passes `--no-parallel`, and with that the matrix passes eight rows out of eight |
| A p95 budget asserted on a single sample | the Host tier's display test compared one cycle against the 200 ms p95 of spec section 8 and failed one run in three on a machine building its own package, at 203 ms against a baseline of 78 to 94. The p95 has a benchmark of its own, with cycles to take a percentile from | the Host test asserts twice the budget, which is what a single sample can carry, and prints both numbers. The p95 stays in `SeatBench display-lifecycle` |
| A passing run saved its own numbers as the baseline | `mergeIntoBaseline` replaced the rows it recognised, so every pass ratcheted the baseline down to that run and the next run failed against it: a clamp p95 of 9542 ns saved over a baseline of 11 000 failed the following run at 11 250, a number the original baseline accepted with room. The rule was already written down: a baseline is regenerated by hand | it adds only rows that are **not** in the file and touches nothing else. Deleting a row is how it gets regenerated |
| A regression checked without looking at the load | a comparison against a baseline is a comparison of two machines' spare capacity, and the rule that a run started above half the cores of load is inconclusive was never implemented. Measured: a preparation cycle at 262 us p95 against a 233 us baseline and a display setup at 402 ms p50 against 358, both inside their budgets, both on a machine running two builds and a browser | the budgets stay gated, which they can be because they are absolute; a baseline regression under a load above half the cores prints `INCONCLUSIVE` with the load average and does not fail the run |
| Three unit tests that read the running machine | `CGGetActiveDisplayList` is **empty** on a Mac whose screen has gone to sleep, though the display is still online, so `DisplayList.active()` does not contain the main display and `TopologyBaseline.capture()` throws `noPhysicalDisplays`. The unit tier is supposed to need nothing of the machine; these three deliberately read it, because the defect they fence is the platform's answer and a fake would only agree with the note. Measured: they failed in a run that started with nobody at the machine, and passed in every run with the screen awake | they are `.enabled(if: aDisplayIsAwake())`, skipped and not relaxed: relaxing them would remove the only place the idiom is checked against the platform |
| An allocation count taken while a real tap was installed | `fence-clamp` installs the **real** tap, so the person's own mouse events are delivered on the fence's thread while the measurement window is open, and `malloc_logger` counts the whole process: 1281 allocations over 20 000 iterations with somebody using the mouse, zero in every run where nobody touched it. The callback's own budget is still zero | the driver counts the events the tap saw that it did not hand over. With any of them, the allocation count is reported `INCONCLUSIVE` instead of failing |
